# TLS and access

## SSL-only PostgreSQL

Every database is configured for TLS during first boot by cloud-init (`bootstrap.sh`, generated by the operator):

- `ssl = on`, with `ssl_cert_file`, `ssl_key_file` and `ssl_ca_file` pointing at `/etc/ssl/certs/pg-server.crt`, `/etc/ssl/private/pg-server.key` and `/etc/ssl/certs/pg-ca.crt`.
- `listen_addresses = '*'` and `port` set from `spec.port` (default 5432).
- Two rules are appended to `pg_hba.conf`:

```text
hostssl all all 0.0.0.0/0 scram-sha-256
hostssl replication all 0.0.0.0/0 scram-sha-256
```

Only `hostssl` rules are added, so a client that connects without TLS is rejected, and passwords are checked with SCRAM-SHA-256. The script only appends these lines; it does not remove whatever default rules the base image ships. There is no source-address restriction in `pg_hba.conf` (`0.0.0.0/0`): who can reach the port is decided by the VLAN the VM is attached to (see [Networking](/networking)).

## Certificates

For each instance the operator generates, once, and stores in the operator-namespace Secret `dbi-<uid>-tls`:

| Item | Detail |
| --- | --- |
| CA | Self-signed, RSA 2048, Common Name `dbaas-ca-pg-<name>`, valid 10 years |
| Server certificate | Signed by that CA, RSA 2048, valid 10 years, Common Name and DNS SAN `pg-<name>` (the VM name), usage server authentication |
| IP SANs | None. The code path to re-issue a certificate with IP SANs exists (`RenewServerCert`) but nothing calls it |

The server certificate and key are written into the VM by cloud-init. The CA **certificate** is published to the tenant in the connection Secret `pg-<name>-connect` under `ca.crt`. The CA **key** stays in `dbi-<uid>-tls`.

Consequences for clients:

- `sslmode=verify-ca` works (this is what the connection Secret advertises): the client checks the server chain against `ca.crt`.
- `sslmode=verify-full` checks the host name. The certificate only names `pg-<name>`, and clients reach the database by IP address, so `verify-full` against the IP fails unless the client resolves `pg-<name>` to the database IP.
- `sslmode=require` encrypts but does not verify the server.
- The certificate is not rotated. There is no rotation feature, and client certificate authentication (mTLS) is not implemented.

## What the operator creates inside PostgreSQL

| Role | Attributes | Purpose |
| --- | --- | --- |
| Master user (`spec.masterUsername`, default `dbadmin`) | `LOGIN CREATEDB CREATEROLE`, **not** superuser; owns the database | Tenant administration |
| `postgres_exporter` | `LOGIN`, member of `pg_monitor` | Metrics exporter on the VM |

The `replicator` role name is reserved (a replication password is generated and stored in `dbi-<uid>-internal`); no replication feature is wired up by the operator.

Bootstrap writes passwords to the database through 0600 files in a postgres-owned tmpfs directory and `format(%I, %L)`, never through command-line arguments, and tests that the master user can really log in over TCP+SSL before the instance can report ready. `/etc/dbaas/bootstrap.env` (which holds the passwords) is shredded at the end of bootstrap. The `pg-<name>-cloudinit` Secret's user data is replaced by an empty `#cloud-config` after the database is ready and monitoring is set up.

## VM password login policy

By default the VM has no password login. Setting `spec.vmPassword` adds a password and `ssh_pwauth: true` through cloud-init, which enables console and SSH password login for the VM's default OS user. The API documents this as for development and debugging only. `vmPassword` is immutable after creation.

A platform administrator can forbid it with the operator setting `security.rejectVMPassword` (default `false`; see [Policy switches](/configuration/policy-switches)). When it is on, a **new** `DBInstance` with a non-empty `spec.vmPassword` stops at preflight with a terminal error, reason `VMPasswordNotAllowed`, and no VM is created. Instances whose VM already exists keep what they were created with.

```yaml
# rejected when security.rejectVMPassword is true
spec:
  vmPassword: "dev-only-password"
```

## SSH and console access

The operator does not install any SSH keys or tenant users. Access to the VM is therefore possible only through the optional `vmPassword`, or through Harvester's own console and tooling, which are outside the operator. Tenants are not expected to log in to the VM: all database administration is done as the master user over SQL.

## What a tenant can and cannot do

| Can | Cannot |
| --- | --- |
| Create, modify and delete `DBInstance` objects in their namespace (per RBAC) | Reference a password Secret from another namespace |
| Read their own `pg-<name>-credentials` and `pg-<name>-connect` Secrets (if RBAC allows reading Secrets) | Read the operator-namespace `dbi-<uid>-internal` and `dbi-<uid>-tls` Secrets (not in their namespace) |
| Create databases and roles as the master user (`CREATEDB`, `CREATEROLE`) | Become PostgreSQL superuser through the master role |
| Connect over TLS with SCRAM-SHA-256 | Connect without TLS |
| Choose the master password (BYO) | Change `networkRef`, `port`, `masterUsername`, `dbName`, `vmPassword` or `credentials` after creation |

The operator ships `dbinstance-viewer-role` (aggregated into the built-in `view` role), plus editor and admin roles for `DBInstance`. Access to Secrets is granted by your own cluster roles, not by these.
